# 客户消息与多媒体处理全链路架构设计

> **版本**：v1.0  
> **更新时间**：2026-08-27  
> **核心原则**：即时流转、事件驱动并发解析、消息占位与冲突拦截（抢占）、工单自动吸收。

---

## 一、核心设计哲学与解决的问题

### 1. 废除生硬的时间盲等
- 摒弃人为设置的短延时（如固定等 2s / 3s）。
- 消息处理以**「事件驱动」**为核心：只要当前批次的所有文件读取/解析完毕，立刻打包提交 Agent。

### 2. 消息占位与冲突拦截（抢占互锁）
- 当 Agent 正在思考或准备向渠道发消息时，若用户发了新消息或新文件，新消息即刻**抢占通道**。
- 正在生成的旧回复在下发前被拦截作废，避免“答非所问”。
- 系统将新输入与已解析好的历史内容合并，重新生成完整回复。

### 3. 多媒体并发读取与异常容错
- 多图片、多 PDF、语音、文件一律进入并发解析任务池。
- 文件读取成功：提取完整文字 / 结构化化验单指标。
- 文件读取失败：标明 `[文件打不开/损坏]`，不阻断流程，随完整上下文一起交给 Agent 做礼貌提示。

### 4. 工单自动吸收报告数据
- 完整的多媒体解析结果到达 Skill-Platform 后，自动入库 `user_recent_files`。
- 新建或流转中的工单 `notes` 自动包含全部报告解析内容，Agent 直接进入专业解读，不再重复要求用户发图。

## 二、系统全链路架构与组件

```
                             企微/聚合 渠道推送
                                     │
                                     ▼
                    ┌─────────────────────────────────┐
                    │      统一用户消息与媒体队列       │
                    │   (Unified Inbound Queue)       │
                    └────────────────┬────────────────┘
                                     │
             ┌───────────────────────┴───────────────────────┐
             ▼                                               ▼
     【纯文本 / 语音转写】                              【图片 / PDF / 附件】
     即刻记录入队                                    创建 MediaTask 并发处理:
                                                     [下载] → [GCS存储] → [OCR/解析]
                                                             │
                                                             ▼
                                                     状态流转:
                                                     - pending / processing
                                                     - completed (含提取内容)
                                                     - failed (含失败原因)
                                                             │
             ┌───────────────────────────────────────────────┘
             ▼
     【触发与分发判定 (Dispatch)】
     - 检查: 队列中是否所有文件都已处理完毕(completed/failed)？
     - 是 ─► 合并所有文本 + 全部附件解析结果 ─► 打包发送至 Skill-Platform
     - 否 ─► 保持等待解析事件通知
             │
             ▼
     【Skill-Platform (Agent 思考与回复)】
     - 写入 user_recent_files
     - 自动同步工单 notes
     - 执行 Agent 推理
             │
             ▼
     【下发前拦截核对 (Preemption Check)】
     - 核对: Agent 思考期间，用户是否有新消息入队？
     - 有新动作 ─► 拦截并作废当前回复，等待新队列处理完重新推理
     - 无新动作 ─► 正常通过渠道发给用户
```

## 三、模块详细规范

### 1. 媒体任务状态机（`MediaTaskManager`）
每个文件作为一个独立的 `MediaTask`：
- `id`: 任务唯一标识（如 msgid）
- `userId`: 用户唯一标识
- `fileName`: 文件名
- `fileUrl`: GCS 永久存储链接
- `status`: `pending` | `processing` | `completed` | `failed`
- `extractedText`: OCR 或 PDF 提取内容
- `error`: 失败原因描述

### 2. 用户待发队列（`UserInboundQueue`）
- 管理单个用户未发送到 Agent 的文字列表和在途媒体任务。
- 每次收到新文字、新媒体、或媒体任务状态变为 `completed`/`failed` 时，触发检查。
- 当且仅当所有媒体任务均处于终态时，执行 `flush`，打包所有文字与解析内容。

### 3. 消息占位与拦截服务（`PreemptionLock`）
- 记录每个用户的 `lastUserActionTimestamp`。
- Agent 开始处理时记录 `taskStartTimestamp`。
- Agent 准备下发回复前，若 `lastUserActionTimestamp > taskStartTimestamp`，立即标记该任务为 `reply_preempted` 并丢弃输出。

## 四、全场景测试矩阵

1. **纯文字**：即时收到即时进入 Agent。
2. **多张图片同时发**：并发 OCR，全部解析完成后一次性合并发送。
3. **文字 + 多附件（先文字后图 / 先图后文字）**：
   - 先图后文字：文字到达时若图已解析完则即刻合并；若图仍在解析中则等图解析完后即刻合并。
   - 先文字后图：文字触发 Agent 后，图片到达触发抢占拦截，图解析完后重新合并触发 Agent。
4. **异常文件容错**：损坏图片标记错误并不阻断流程。
5. **工单数据载入**：工单自动包含所有附件数据，直接进入分析。
